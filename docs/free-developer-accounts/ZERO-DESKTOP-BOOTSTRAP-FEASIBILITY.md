# Zero-desktop bootstrap feasibility

Reviewed 27 November 2026 against the physical Safari result on stock iOS 27.2.1 and current platform documentation. No reviewed mechanism meets every requirement. The specific gap is an authorized **first installation from Safari of a visitor's free Personal Team app**. iOS 27 does support a new, explicitly authorized wireless pairing without a cable. That advances the device-development workflow without giving a webpage the role of an installation client.

## Evidence and scope

- Zag Store already signs on-device with Personal Team credentials. The signed Zag Store and minimal standalone probe passed independent signature, profile and target eligibility checks. The probe eliminated most app-specific packaging factors.
- The existing device archive logged two exact bundle-linked failures on 27 November 2026 at 01:13:53 and 01:14:07 GMT. `installd` returned `MIInstallerErrorDomain` **111** and `ApplicationVerificationFailed`, explicitly identifying a free provisioning profile disallowed from the installation source. `IXUserPresentableErrorDomain` **1** was the user-facing wrapper. The probe reached native package validation. The recorded failure was specific to installation source even though device capacity remained unknown. See the [experiment record and collector procedure](WEBSITE-INSTALL-FEASIBILITY.md#confirmed-rejection-on-ios-2721).
- This directly establishes a restriction for the tested Safari OTA source on that build. Conclusions about other channels below follow from their documented eligibility or reviewed implementation. No new device experiment was run.
- Keep these boundaries separate. Portal enrollment registers a target for development. A signing certificate and provisioning profile authorize a particular code identity, device and set of entitlements. Pairing authorizes a participant to connect to device services. The selected installation source has its own acceptance rules. [Apple provisioning technote](https://developer.apple.com/documentation/technotes/tn3125-inside-code-signing-provisioning-profiles)

## Pairing and browser boundary

Apple's physical-pairing security guide describes the host trust model for USB and the associated Wi-Fi connection, including trust and authenticated sessions. For the current first-pairing answer use the newer Xcode 27 documentation. Device Hub can pair iOS 27 devices over the network with local device approval. An existing pairing and a USB cable are therefore unnecessary for that workflow. A participating native client is still required. There is no documented Safari API that joins this pairing flow as the developer peer or obtains an authenticated RSD session. [Physical pairing security](https://support.apple.com/guide/security/physical-pairing-model-security-secadb5b6434/web) · [Xcode 27 wireless pairing](https://developer.apple.com/documentation/xcode-release-notes/xcode-27-release-notes)

CoreDevice is a host developer tool. The reviewed open-source transport separates trust establishment, tunnel creation, RSD discovery and the requested service. Discovering a service or reaching a socket does not authorize it. Installation Proxy is an explicit device-service operation. A browser URL, portal device registration, ordinary LAN access, a VPN profile or a generic user consent dialog does not provide the native pairing client, records or service authority. Apple's browser integration for alternative distribution forwards eligible website requests to MarketplaceKit under that program's policy. It does not expose a developer-service transport to the website. [Transport source guide](https://github.com/doronz88/pymobiledevice3/blob/master/docs/guides/ios17-tunnels.md) · [Installation Proxy source interface](https://github.com/libimobiledevice/libimobiledevice/blob/master/include/libimobiledevice/installation_proxy.h) · [MarketplaceKit browser integration](https://developer.apple.com/documentation/marketplacekit/enabling-alternative-distribution-app-installation-in-a-browser)

## Open-source bootstrap audit

- **AltStore Classic** uses AltServer on a computer for initial installation. **AltStore PAL** is a distinct notarized MarketplaceKit channel. Its website bootstrap is evidence for Apple's authorized marketplace mechanism only. [Classic installation](https://faq.altstore.io/altstore-classic/how-to-install-altstore-windows) · [AltStore PAL](https://altstore.io/)
- **SideStore** documents a computer for first install, with iloader and a pairing artifact. LocalDevVPN supports on-device operation after bootstrap. The iloader source describes signing and installing apps and importing the pairing file. Running later without a computer does not change the first-install requirement for that documented route. [SideStore prerequisites](https://docs.sidestore.io/docs/installation/prerequisites.html) · [SideStore install source](https://github.com/SideStore/SideStore-Docs/blob/main/docs/installation/install.mdx) · [iloader source](https://github.com/nab138/iloader)
- **SideInstaller / siboot** is a newer and materially different iOS 27 claim. The project's actual install page requires obtaining the native Open Minis terminal and LocalDevVPN from the App Store before running the bootstrap within that terminal. Its source entry point runs in the native terminal context, and SideInstaller's implementation notes describe paired RSD access and Installation Proxy for the eventual app installation. The project reports first-time on-device pairing with user confirmation and no enterprise certificate in its current terminal route. Older project instructions also describe enterprise OTA. These routes must be evaluated separately. The newer flow can begin with a link in Safari and does not require prior pairing according to the project. It performs the installation in an additional native execution environment after the user leaves Safari. It is credible evidence that cable-free pairing and computer-free developer-tool workflows deserve separate treatment, but it is not a direct Safari installation, nor evidence of an Apple-supported browser bootstrap. No code from it was run or integrated. [Current installation prerequisites](https://sideinstaller.net/install.html) · [siboot source entry point](https://github.com/FrizzleM/siboot/blob/main/minis/install.sh) · [SideInstaller implementation notes](https://github.com/FrizzleM/SideInstaller/blob/main/NOTES.md)
- **LiveContainer** runs inside an installed host and still needs that host installed through one of the available routes. Its runtime and app handling do not provide the first native install from Safari. [LiveContainer source](https://github.com/LiveContainer/LiveContainer)

## Decision and fallback

Keep website discovery, download and instructions separate from installation. Do not build browser credential collection, a remote pairing relay, a configuration-profile installer, an MDM trial, or a new Personal Team OTA publisher. None addresses the documented source or client boundary. Do not use an exploit, hidden entitlement, borrowed pairing record or enterprise certificate as a substitute for admission.

**Closest supportable option that retains free Apple ID signing** is one-time assisted development setup. The user opens zagstore.app, authorizes first pairing in a nearby trusted Xcode 27 Device Hub, and uses the documented device-development install flow under their Personal Team. No purchased certificate, previous pairing, cable on iOS 27, or previously installed sideloading app is needed. This is an existing tool workflow and requires a nearby Mac, so it is explicitly outside the original zero-desktop requirement. Any subsequent hands-off Zag Store renewal depends on a compatible verified installation, preserved pairing and the existing renewal prerequisites. Do not collect or retain the user's credentials or pairing material as part of assistance. A fully managed or mass-distributed service is outside the intended scope of Personal Team development. [Device Hub](https://developer.apple.com/documentation/xcode/managing-your-simulated-and-physical-devices-in-device-hub) · [Apple developer account overview](https://developer.apple.com/help/account/basics/about-your-developer-account/)

If **zero desktop and direct website initiation** are higher priorities than visitor-side free signing in a separate product decision, evaluate whether Zag Store qualifies for authorized EU Web Distribution, including app eligibility and notarization. An approved marketplace can reach additional supported regions with a marketplace handoff. Publisher approval and distribution review remain gates. Do not advertise that the current Zag Store feature set has passed them. [Web Distribution](https://developer.apple.com/support/web-distribution-eu/) · [App Review and notarization guidelines](https://developer.apple.com/app-store/review/guidelines/)

Reopen implementation only on new evidence of an Apple-supported Safari handoff to a Personal Team installation service, or explicit agreement to a different distribution model. This decision preserves the signing engine, preview tooling and diagnostic collector.
